Record — openshift / finalizers
Symptom

Namespace has sat in Terminating for forty minutes and will not go.

Command, as run 
# strip finalizers from every Argo resource in the namespace
for obj in $(oc get applications.argoproj.io,\
    applicationsets.argoproj.io,appprojects.argoproj.io \
    -n <NAMESPACE> -o name); do
  oc patch $obj -n <NAMESPACE> --type merge \
    -p '{"metadata":{"finalizers":null}}'
done
What it costs you

Orphans every resource the app managed. ArgoCD stops tracking them and will never prune or reconcile them again. Delete the workload properly first if you can.

Why this exists

The command you need already worked once. You just cannot find it.

The problem

Search gives you documentation, not experience.

Something is broken and you have maybe ten minutes. What comes back is the official reference reprinted by a content farm, a confidently wrong answer with syntax that has never existed, and a thread from 2019 about a version you are not running.

The command that actually fixed this last time was in a scrollback buffer you closed three months ago.

What it costs

The dangerous commands are the ones that look scoped.

Untested commands rarely fail loudly. They fail quietly, and later, and somewhere else.

oc delete crd applications.argoproj.io
→ deletes every ArgoCD Application on the cluster, in every namespace. There is no per-namespace opt-out.

The page you copied that from did not tell you, because nobody who wrote it had run it anywhere that mattered. Same story for podman rm -a, which removes every stopped container on the host rather than the one you were debugging, and sudo fuser -k <PORT>/tcp, which kills whatever holds the port with no graceful shutdown and no prompt.

What this is

9 sheets, 138 commands, every one of them traceable.

Each command here came out of a recorded terminal session and carries a reference back to the dump line it was typed on. Commands that cannot be traced never make it onto the page — that rule is enforced by a pipeline, not by good intentions.

Where a command is strange but worked, it is kept and flagged rather than quietly corrected: a sudo gem install --user-install whose flags contradict each other is still what ran successfully on the machine it was recorded from. Where a command destroys something, the sheet says exactly what.

How a sheet is made

Four stages, and a command can only survive all four by being real.

This is a genuine sequence — each stage can only run on the output of the one before it, and the third stage physically cannot emit a command the second one did not record.

STAGE 1

Record

A real working session is dumped to _sources/. Those dumps hold live tokens and hostnames, so they are gitignored and never leave the machine.

STAGE 2

Extract

Each command is structured into commands.yml with a source_ref pointing at its dump line. Credentials and identifiers are replaced here, once, at the only stage that reads raw source.

STAGE 3

Write

The sheet is generated from that file alone. No source_ref, no output — which is why a plausible-sounding command that nobody ran cannot appear.

STAGE 4

Audit

A reviewer reads the raw dump rather than a summary and diffs it against the sheet in both directions: invented commands and dropped ones. It reports; it never rewrites a working command.

The pipeline is its own open-source project — cheatsheet-forge — if you want to run it against your own recorded sessions.

Ask

Stuck on something that is not here yet?

Ask it as an issue. If the answer exists in a session I have recorded, it becomes a new entry on the relevant sheet, with its trace attached like everything else.

Three things that always get a reply:

  • A command here did not work. That is a defect and I want it.
  • A command here is dangerous and not labelled. That is the worst kind of bug on this site.
  • A technology you want covered. Requests decide what gets recorded next.
