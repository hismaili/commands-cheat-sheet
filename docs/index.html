Anatomy of an entry · example from OpenShift
Symptom

A namespace has been Terminating for forty minutes and will not delete.

Command, as run 
# strip finalizers from every Argo resource in the namespace
for obj in $(oc get applications.argoproj.io,\
    applicationsets.argoproj.io,appprojects.argoproj.io \
    -n <NAMESPACE> -o name); do
  oc patch $obj -n <NAMESPACE> --type merge \
    -p '{"metadata":{"finalizers":null}}'
done
Consequence

Orphans every resource the app managed. ArgoCD stops tracking them and will never prune or reconcile them again. Delete the workload properly first if you can.

Why this exists

The command exists. Finding it again is the problem.

The problem

Documentation is organised by flag. Problems are not.

Every tool in the stack fails in a small number of recognisable ways, and the command that resolves each one already exists. It has usually been run before, on this machine, by you. Retrieval is the constraint, not knowledge.

Vendor references index by subcommand and flag. The problem in front of you presents as a symptom, and the session where it was last resolved is three months gone.

What it costs

A command without its context is not reusable.

A command saved with no note about what it was for, which problem it closed, or what it removes is a liability rather than an asset. It gets pasted into the wrong situation, or into a live system whose blast radius nobody wrote down.

oc delete crd applications.argoproj.io
→ deletes every ArgoCD Application on the cluster, in every namespace. There is no per-namespace opt-out.

podman rm -a removes every stopped container on the host, not the one being debugged. sudo fuser -k <PORT>/tcp kills whatever holds the port, with no graceful shutdown and no prompt. Each is correct, and each is documented. What is absent from the documentation is what it takes with it.

What this is

A working notebook: 169 commands across 10 technologies.

Each entry records four things: the command, what it is for, the problem it resolves, and the session it came from. Where a command destroys something, the entry states what. A command that cannot be traced does not reach the page, and that rule is enforced by the build rather than by intent.

Where a command is unusual but worked, it is kept and annotated rather than corrected. A sudo gem install --user-install whose flags contradict each other is still what ran successfully on the machine it was recorded from.

Start with a cheat sheet, or open the symptom index if the problem is already in front of you.

How a sheet is built

Four stages. A command reaches the page only by surviving all four.

Each stage runs on the output of the one before it. The third stage cannot emit a command that the second one did not record.

STAGE 1

Record

A working session is captured to _sources/. Those captures hold live tokens and hostnames, so they are gitignored and never leave the machine.

STAGE 2

Extract

Each command is structured into commands.yml with a source_ref pointing at its dump line. Credentials and identifiers are replaced here, once, at the only stage that reads raw source.

STAGE 3

Write

The sheet is generated from that file alone. No source_ref, no output. A plausible command that was never run has no way onto the page.

STAGE 4

Audit

A reviewer reads the raw session rather than a summary and compares it against the sheet in both directions: commands invented, and commands dropped. It reports. It does not rewrite a working command.

The pipeline is an open-source project of its own, cheatsheet-forge, and can be run against your own recorded sessions.

Ask

Not covered here yet?

Open it as an issue. If a recorded session covers the answer, it becomes a new entry on the relevant sheet, with its trace attached like every other entry.

Three kinds of issue always get a reply:

  • A command here did not work. That is a defect, and I want the issue.
  • A command here is destructive and not labelled as such. That is the most serious defect this site can have.
  • A technology you want covered. Requests determine what gets recorded next.
